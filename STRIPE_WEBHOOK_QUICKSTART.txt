STRIPE WEBHOOK — QUICK START
================================================================================

2026-08-27: This file previously described a now-retired endpoint
(src/app/api/webhooks/stripe/route.ts, /api/webhooks/stripe). That route
returns 410 Gone today. This rewrite describes the live handler.

WHAT'S LIVE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Handler: server/webhooks/stripe.ts
  Route:   POST /api/stripe/webhook   (registered in server/_core/app.ts)

  - Verifies the Stripe signature against EVERY brand's configured secret
    (see "PER-BRAND SECRETS" below), not just one — a single endpoint path
    correctly serves authichain.com, qron.space, strainchain.io, and
    govchain.us, each of which can have its own Stripe webhook secret.
  - Handles: customer.subscription.created, customer.subscription.updated,
    customer.subscription.deleted, invoice.payment_succeeded, invoice.paid,
    invoice.payment_failed, checkout.session.completed,
    checkout.session.expired
  - Idempotency: dedups against the activity_log table (by event.id)
  - Writes to: subscriptions, revenue_records, activity_log, notifications

WHAT DOES IT DO?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Event: customer.subscription.created / customer.subscription.updated
  → UPSERT subscriptions (plan, status, quota, billing cycle, period dates)
  → On new + active/trialing: send welcome email
  Purpose: Keep local subscription state in sync with Stripe; onboard users

Event: customer.subscription.deleted
  → UPDATE subscriptions SET status='cancelled'
  Purpose: Track cancellations

Event: invoice.payment_succeeded / invoice.paid
  → INSERT revenue_records (amount, currency, plan, ids)
  → UPDATE subscriptions SET status='active'
  Purpose: Revenue reporting, keep subscription healthy after payment

Event: invoice.payment_failed
  → UPDATE subscriptions SET status='past_due'
  → INSERT notifications ("Payment Failed") for the affected user
  Purpose: Start dunning, warn the customer in-app

Event: checkout.session.completed
  → (one-time service orders only) run fulfillment via
    handleServiceOrderPayment
  Purpose: Fulfill non-subscription purchases

Event: checkout.session.expired
  → send checkout-recovery email with a discount code
  Purpose: Win back abandoned checkouts

ALL EVENTS:
  → logAutomationAudit(...) → activity_log (compliance / debugging)
  → First check: hasWebhookEventProcessed(event.id) → activity_log
    (idempotency — duplicate deliveries are logged and skipped)

PER-BRAND SECRETS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  shared/brands.ts declares, per brand, which env var holds that brand's
  Stripe webhook signing secret (billing.webhookSecretEnv):

    authichain   → STRIPE_WEBHOOK_AUTHICHAIN_SECRET
    qron         → STRIPE_WEBHOOK_SECRET
    strainchain  → STRIPE_WEBHOOK_SECRET
    govchain     → STRIPE_WEBHOOK_SECRET

  handleStripeWebhook collects every distinct secret named above (plus
  STRIPE_WEBHOOK_SECRET as a fallback) and tries each one against the
  incoming signature until one verifies. Set BOTH env vars in your
  deployment — you do not need a separate route per brand.

SETUP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. FOR EACH BRAND DOMAIN, ADD A STRIPE WEBHOOK ENDPOINT
   → https://dashboard.stripe.com/webhooks → Add endpoint
   → URL: https://<brand-domain>/api/stripe/webhook
     (same path for every brand — e.g. https://authichain.com/api/stripe/webhook
      and https://qron.space/api/stripe/webhook)
   → Events: customer.subscription.created, customer.subscription.updated,
              customer.subscription.deleted, invoice.payment_succeeded,
              invoice.paid, invoice.payment_failed,
              checkout.session.completed, checkout.session.expired
   → Click "Reveal signing secret" → copy (starts with whsec_)

2. SET THE ENV VARS IN YOUR DEPLOYMENT
   → authichain.com's secret     → STRIPE_WEBHOOK_AUTHICHAIN_SECRET
   → every other brand's secret  → STRIPE_WEBHOOK_SECRET
     (if two non-authichain brands ever need different secrets, give the
      brand its own entry in shared/brands.ts's webhookSecretEnv and set
      that env var — the handler picks up any brand's configured var
      automatically, no code change needed beyond that one line)

3. DEPLOY / REDEPLOY so the new env vars are read

DONE! Webhooks are now active for every brand behind this one endpoint.

TROUBLESHOOTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: Webhook returns 400 "Webhook Error"
  → Signature didn't match ANY configured secret. Confirm the secret in your
    deployment env matches the one shown in Stripe Dashboard for THAT
    specific endpoint — authichain.com's endpoint uses
    STRIPE_WEBHOOK_AUTHICHAIN_SECRET, the others use STRIPE_WEBHOOK_SECRET.

Problem: Requests to /api/webhooks/stripe get 410 Gone
  → That endpoint is retired on purpose. Point Stripe at /api/stripe/webhook.

Problem: Events show 200 in Stripe Dashboard but nothing changed in the app
  → Check activity_log for a row with that event's id (confirms the handler
    ran). If present, check the relevant table (subscriptions,
    revenue_records) and DATABASE_URL. If absent, check server logs for
    "[stripe-webhook]" errors.

Problem: Duplicate rows / emails for the same event
  → Should not happen — hasWebhookEventProcessed checks activity_log before
    any side effect runs. If you see it, check activity_log for a genuine
    idempotency-check failure (e.g. DATABASE_URL misconfigured, in which
    case hasWebhookEventProcessed silently returns false and side effects
    can repeat).
