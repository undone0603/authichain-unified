## Why the spec overestimated salvage value

A retrospective note to inform future consolidation efforts:

The original Phase 0 scan agent operated by reading commit messages, file paths, and dependency lists. That signal mostly tracked **what code looks like** (file size, deps installed, recent activity), not **what the consuming codebase actually needs**. The misses cluster around two patterns:

1. **"Sophisticated → simple" lifts.** The spec assumed source code with real-looking domain logic was salvageable. But unified's tRPC + Drizzle + GPT-4-Vision-via-`_core/llm.ts` stack was already strictly more capable than the Next.js prototype's external-proxy + Supabase-client patterns. The newer code obsoletes the older code.

2. **Coupling to source's data shapes.** UI components (4.6) and routes (4.2, 4.3) depend on the source's response shapes, which differ from unified's. Salvage requires either porting the data layer too (turning a lift into a feature) or rewriting the UI/route to match unified's shape (turning a lift into a write).

Lesson: **for future salvage scans, always grep the destination for already-implemented capabilities before scoping any lift task**, and reject lifts where the destination has equivalent or better functionality. A 1-hour reconnaissance against the destination saves N hours of avoided lift work later.
