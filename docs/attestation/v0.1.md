# AuthiChain Attestation Contract v0.1

This directory is the reference implementation of the AuthiChain v0.1 attestation contract.

## Contract

An attestation is a signed statement connecting an AuthiChain provider-scoped `object_id` to a physical product identifier where available (`gtin` + `serial` or `lot`). The contract deliberately separates:

- **Evidence** — what AuthiChain observed or anchored.
- **Decision** — `verified`, `warning`, or `blocked`.
- **Status** — `active`, `revoked`, or `unknown`.
- **Issuer** — the organization controlling the signing key.
- **Subject** — the object being attested.

The signed representation is a compact JWS using **Ed25519 / EdDSA**. The JWS protected header uses `typ=AC-ATTESTATION+JWS` and a `kid` that identifies the issuer key.

## Canonicalization

The JSON payload is serialized deterministically before signing: object keys are sorted recursively, arrays retain their supplied order, and JSON is emitted without insignificant whitespace. This implementation is in `packages/verifier/src/index.ts` (`canonicalize`).

## Endpoints

### `POST /api/v1/attestation`

Accepts a v0.1 JSON payload and returns:

- the validated payload;
- a compact JWS;
- the signing key ID.

Requires `AUTHICHAIN_ATTESTATION_PRIVATE_KEY_B64` in the deployment environment. The value is a base64-encoded PKCS#8 Ed25519 private key. Never commit the private key.

Optional environment variables:

- `AUTHICHAIN_ATTESTATION_KEY_ID` — explicit `kid`; otherwise the JWK thumbprint is used.

### `PUT /api/v1/attestation`

Same contract as `POST /api/v1/attestations/verify` below.

### `POST /api/v1/attestations/verify`

Provides the consumer-facing verification contract. It verifies the JWS against this deployment's public key and evaluates the attestation's freshness, status, and decision. A result is `valid=true` (HTTP 200) only when the attestation is unexpired, `active`, and `verified`. Responses expose `cryptographic_status`, `issuer_status`, `claim_status`, and `overall_valid`; when a durable lifecycle event exists they also expose its event ID, effective time, and reason code. Revoked, expired, warning, or blocked attestations remain cryptographically inspectable but return `valid=false` (HTTP 409) with `decision`, `status` (`expired` once `expires_at` has passed), `reasons` and the attestation preserved. A signature, key or schema failure is HTTP 400. Pass `expected_object_id` to bind the check to the object in hand.

On the edge router this is `worker-app/attestation-api.ts`; `/api/v1/attestation/verify`, `/api/attestations/verify` and `/api/attest/verify` are aliases. The status in a signed payload is the status at issuance; the durable registry is the live lifecycle status source for revoked and superseded claims.

### `POST /api/v1/attestations/:id/revoke`

Requires issuer authorization and a JWS whose attestation ID matches `:id`. The optional `Idempotency-Key` header (or `idempotency_key` JSON field) makes retries issuer-scoped and returns the original lifecycle event instead of creating a duplicate.

### `POST /api/v1/attestations/:id/supersede`

Requires issuer authorization, the original `jws`, and a `replacement_jws`. Both JWS values must identify the same currently trusted issuer, and their attestation IDs must differ. The original attestation receives durable status `superseded` with `supersedes_attestation_id` pointing to the replacement. `Idempotency-Key` is issuer-scoped.

### `GET /api/v1/attestations/:id/status`

Returns the durable claim status and the effective lifecycle event metadata. The durable registry is fail-closed for verification.

### `GET /.well-known/jwks.json`

Publishes the active public verification key as a JWKS. Only public key material is returned.

## Interoperability rules

1. `object_id` is provider-scoped and must not be treated as globally unique without the issuer identity.
2. A `gtin` identifies a product class; `serial` identifies an item when supplied; `lot` identifies a production lot.
3. A copied QR code or transferred label is **not** proven authentic by the existence of a valid signature alone. The consuming verifier must evaluate subject mapping, evidence continuity, freshness, revocation, and destination policy.
4. `warning` and `blocked` are explicit trust decisions, not signature failures.
5. A valid signature proves integrity and issuer control of the attestation; it does not independently prove the physical item matches the attested subject.

## Conformance fixtures

`fixtures/attestation-v0.1-valid.json` is the canonical payload fixture.

`fixtures/attestation-v0.1-valid.jws` is a cryptographically valid Ed25519 compact JWS for that payload.

`fixtures/attestation-v0.1-tampered.jws` changes the decision without recomputing the signature and must fail verification.

`fixtures/attestation-v0.1-jwks.json` contains the public fixture key only.

These fixtures intentionally contain no production secrets.
