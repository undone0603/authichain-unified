# StrainChain intake playbook

## Purpose

Use this internal playbook to classify inbound StrainChain requests, protect
operator information, and track delivery. It does not authorize outreach,
pricing, technical commitments, or public claims; those remain governed by the
[operating charter](../OPERATING_CHARTER.md).

## Intake classification

Classify each request by persona, operating state, and license status before
assignment:

| Persona              | Handling path                                                            |
| -------------------- | ------------------------------------------------------------------------ |
| Cultivator           | Evaluate onboarding fit after license verification.                      |
| Lab                  | Evaluate integration fit after accreditation and license verification.   |
| Dispensary           | Evaluate partnership fit after license verification.                     |
| Multi-state operator | Escalate for enterprise review after license verification.               |
| Consumer             | Provide public product information; do not create an operator follow-up. |
| Regulator            | Escalate for compliance and policy review.                               |

Treat a license as unverified until it has been checked against the applicable
state source. A license check establishes only the status needed for intake; it
does not validate a product, laboratory result, or provenance claim.

## Data handling

- Keep license numbers, batch identifiers, and submitter details in the
  approved intake system.
- Do not export, forward, or disclose intake data without written approval.
- Record only the minimum information needed to classify and assign the
  request.
- Do not put operator data in issues, public documentation, or prompts.

## Assignment and completion

1. Assign an internal owner after classification and verification.
2. Use the persona to select the appropriate approved information or demo
   material; verify that any referenced route is current before sharing it.
3. Create an engineering follow-up only for a documented technical requirement;
   do not promise a custom QR, StoryMode asset, integration, or delivery date.
4. Mark a request delivered only after the requester receives the approved
   information, walkthrough, or asset.
5. Record unresolved questions and escalate requests that require pricing,
   external contact, public claims, or changes to the product boundary.

## Product boundaries

StrainChain passports are defensive provenance records. Follow the decisions in
[the genetics-passport strategy](../strategy/strainchain-genetics-passport.md):
do not present the service as a breeding program, genetics marketplace, METRC
replacement, or laboratory certification authority.
